# Стресс-тест

Набор скриптов для проверки isho на объёме данных: 1000 пользователей,
1000 проектов, 1000 тегов, 1000 тем форума и по 200 сообщений в каждой
(200 000 сообщений). Данные создаются и удаляются отдельными командами.

## Что создаётся

| Сущность | Количество | Маркер |
|---|---|---|
| Пользователи | 1000 | `stresstest_0001…1000`, почта `…@stress.isho.local` |
| Теги | 1000 | slug `stress-teg-…` |
| Проекты | 1000, опубликованы | slug `stress-project-…` |
| Скриншоты | по 1 на проект | файлы в `api/public/media` |
| Темы форума | 1000 | slug `stress-topic-…` |
| Сообщения | по 200 в теме | всего 200 000 |

Половина тем лежит в разделе `projects` и привязана к опубликованным проектам,
половина — в остальных разделах. Авторы ответов — разные стресс-пользователи,
часть сообщений содержит цитаты, Markdown и длинные тексты. Все стресс-аккаунты
имеют пароль `stress1234`, почта уже подтверждена (письма не отправляются).

Сид идемпотентный: повторный запуск досоздаёт недостающее, поэтому прерванный
прогон можно продолжить той же командой.

## Локально

Все команды — из каталога `api`:

```powershell
# 1. Сборка задач
crystal build tasks.cr -o bin/tasks.exe

# 2. Проверка доступа к БД и текущих размеров
.\bin\tasks.exe db.stress.stats

# 3. Смоук на маленьких числах (сначала так, потом полный прогон)
.\bin\tasks.exe db.stress.seed --users=5 --projects=5 --tags=5 --topics=2 --posts-per-topic=3 --screenshots=1
.\bin\tasks.exe db.stress.stats
.\bin\tasks.exe db.stress.cleanup --yes

# 4. Полный прогон (по умолчанию 1000/1000/1000/1000/200, 1 скриншот)
.\bin\tasks.exe db.stress.seed
.\bin\tasks.exe db.stress.stats

# 5. Приложение и замеры
cd ..
.\dev.ps1
# в другом окне, из корня репозитория:
node stress/probe.mjs --label local

# 6. Удаление (сначала dry-run, потом --yes)
cd api
.\bin\tasks.exe db.stress.cleanup
.\bin\tasks.exe db.stress.cleanup --yes
# вернуть диск после удаления (блокирует таблицы):
.\bin\tasks.exe db.stress.cleanup --yes --vacuum
```

Скриншоты требуют ImageMagick: на Windows задача сама подхватывает Scoop-путь
(`%USERPROFILE%\scoop\apps\imagemagick\current`), на Linux нужен пакет
`imagemagick`. Если медиа не нужны, запускайте с `--screenshots=0` — сид будет
заметно быстрее.

Параметры сида: `--users`, `--projects`, `--tags`, `--topics`,
`--posts-per-topic`, `--screenshots`. `--posts-per-topic` считает **все**
сообщения темы, включая стартовое: при 200 получается 1 + 199 ответов.

## Зонд нагрузки

`stress/probe.mjs` не требует зависимостей (Node 22). Он сам находит стресс-данные
через API и меряет:

- API: здоровье, теги, каталог (первая и последняя страница), поиск, фильтр по
  тегу, проект, разделы форума (первая/последняя), тему (первая/последняя),
  профиль;
- SSR Nuxt: главная, форум, раздел, тема, проект, профиль;
- последовательные запросы и конкурентность 5/10 (`--concurrency`), p50/p95/max,
  ошибки, RPS, размер ответа.

```powershell
node stress/probe.mjs --label local
node stress/probe.mjs --base http://localhost:3000 --api-base http://localhost:4000 --runs=10 --concurrency=5,10
```

Результат печатается таблицей и сохраняется в `stress/results/<label>-<время>.json`.
Файлы результатов в git не попадают.

## VPS

Сначала задеплойте сборку с новыми задачами (на сервере нет Crystal):

```powershell
$env:ISHO_SSH_PASSWORD = '<пароль root>'
.\deploy\deploy.ps1
```

Дальше `stress/remote.ps1` (plink/pscp, как в deploy):

```powershell
# состояние сервера, память, диск, размеры таблиц
.\stress\remote.ps1 -Action preflight

# бэкап перед экспериментом
.\stress\remote.ps1 -Action backup

# полный сид (обязателен -Yes: данные публикуются)
.\stress\remote.ps1 -Action seed -Yes

# замеры на самом сервере: Nuxt :3000 и API :4000 напрямую
.\stress\remote.ps1 -Action probe -Label vps

# удаление — отдельной командой, в любой момент
.\stress\remote.ps1 -Action cleanup            # dry-run
.\stress\remote.ps1 -Action cleanup -Yes       # удалить
.\stress\remote.ps1 -Action cleanup -Yes -Vacuum
```

`-Action seed` можно запускать с меньшими числами:
`-Users 100 -Projects 100 -Tags 100 -Topics 10 -PostsPerTopic 20`.

Полезные ручные команды на сервере:

```bash
runuser -u isho -- bash -c 'set -a; . /etc/isho/api.env; set +a; cd /srv/isho/api && ./bin/tasks db.stress.stats'
runuser -u isho -- bash -c 'set -a; . /etc/isho/api.env; set +a; cd /srv/isho/api && ./bin/tasks db.stress.cleanup --yes'
journalctl -u isho-api -u isho-web -f
systemctl show -p MemoryCurrent isho-api isho-web
free -m; df -h /
```

Прогон на 709 МБ / 1 vCPU может занять десятки минут и на время сида заметно
нагрузить сайт. Это тестовый стенд; на живом сайте сначала сделайте бэкап и
предупредите пользователей.

## Результат локального прогона (2026-10-22)

Машина: i7-8700K (6 ядер / 12 потоков), 32 ГБ RAM, PostgreSQL 16 в Docker,
Nuxt dev-сервер и API dev-сборка.

| Метрика | Значение |
|---|---|
| Сид 1000/1000/1000/1000/200 + 1 скриншот | 8 мин 20 с |
| — пользователи и теги | 8 с |
| — проекты и скриншоты | 4 мин 07 с |
| — темы и 200 000 сообщений | 4 мин 03 с, ~820 сообщений/с |
| БД до / после | 9.4 МБ / 155.6 МБ (+146.2 МБ) |
| `forum_posts` | 143.0 МБ (heap 129.6, indexes 13.4) |
| Медиа (1000 скриншотов) | 282.7 МБ (~283 КБ на скриншот) |
| Итого данных | ~438 МБ |
| Очистка | 20.0 с |
| `VACUUM (FULL)` после очистки | 155.6 МБ → 9.5 МБ, 0.3 с |
| API p95 c=1 → c=10, теги | 17 → 121 мс |
| API p95 c=1 → c=10, обсуждения проектов | 28 → 100 мс |
| API p95 c=1 → c=10, тема с 200 сообщениями | 9 → 64 мс |
| SSR p95 c=1 → c=10, главная | 147 → 960 мс |
| SSR p95 c=1 → c=10, страница проекта | 36 → 192 мс |
| Ошибок за 594 запроса | 0 |

Главная — единственное место, которое заметно проседает под конкурентностью:
1000 тегов отдаются целиком, SSR рендерит их все, ответ главной ~256 КБ.
API и страницы тем/проектов на этом объёме остаются быстрыми. Результаты
зонда лежат в `stress/results/local-full-2026-10-22T07-33-44.json`.

## Безопасность

- Сид и очистка трогают только записи с маркерами (`stresstest*`,
  `stress-project-*`, `stress-teg-*`, `stress-topic-*`).
- `db.stress.cleanup` без `--yes` ничего не удаляет.
- Если стресс-аккаунт владеет проектом/темой без маркера или писал в чужую
  тему, очистка останавливается и перечисляет проблемы. `--force` разрешает
  удалить только «заблудшие» сообщения (через `DeleteUserContent`, с пересчётом
  счётчиков), но не даёт удалять чужие проекты и темы.
- `VACUUM (FULL)` блокирует таблицы; на живом сайте его лучше делать в окно
  обслуживания. Без него место на диске не уменьшится, хотя строки исчезнут.
- Удаление пользователей в очистке идёт через `User::DeleteOperation`, а не
  `DeleteUserAccount`: аккаунтов много, а `DeleteUserAccount` сканирует все теги
  на каждый аккаунт. Файлы скриншотов удаляются заранее, потому что каскад БД
  не вызывает Latch.
